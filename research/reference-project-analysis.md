# 调研：巴黎城市时空文化地图

## 调研摘要

参考项目 **StoryMap**（cuizicheng1024/storymap，线上 storymap.opendeploy.site）是一个"历史人物时空分析"产品：以**人物**为主体，把一个人的一生展开成地图轨迹 + 时间轴，面向**中学语文/历史跨学科教学**。其工程骨架高度成熟且可复用——Markdown 语料库 → 解析器 → 数据构建 → 静态 HTML 产物 → Pages 发布的全链路，加上首页星图/地图双视图、详情页时间轴↔地图双向联动、AI 人格化对话、关系图谱穿越等完整交互。

我们要做的新项目在**底层框架与交互链路上与之同构**，但有三处本质差异：① 地域从境内转向**境外（MVP 聚焦巴黎）**；② 主体从**人物**转向**城市 POI**；③ 调性从**教学向**转向**旅游 + 微文艺 + 娱乐轻松向**（用户明确）。第三点是用户在需求过程中补充的，它并非文案差异，而会反向决定 POI 入选标准、内容字段和故事线组织方式。

三条用户约束贯穿全程：**最小化修改**（尽量保留 StoryMap 原始代码结构）、**功能降级优先**（境外做不了的先降级/舍弃）、**降级前必须确认**（任何舍弃需事先沟通）。另有一条内容侧硬要求：**语料库必须自建，不能偷懒**——这是本项目真正的护城河。

### A. 工程架构与数据流水线

```
Flow A：语料 → 静态页（核心生产链路）
storymap/examples/story/*.md（539 份人物 Markdown，单一数据源）
  ↓ core/parsers.py :: parse_story_document
  ↓ profile/builder.py :: build_profile_data
  ↓ profile/renderer.py + templates/profile_page.html（注入 __EXPORT_DATA__）
artifacts/story_map/{人物}.html（534 张静态页）

Flow B：静态页 → 首页星图

  ↓ tools/build/homepage/main.py

Flow C：新对象生成（Agent 链路）

Flow D：运行时 FastAPI（可选）
/generate、/task、/api/ai/proxy、/coords/bulk
```

**关键工程约束（复用时必须知道）：**
- CI 入口固定：`cli/generate_pure_story_map.py`、`tools/build_all.py`、`tools/build/homepage/main.py`、`tools/validate_story_markdown.py`
- 语料路径 `storymap/examples/story/` 被 GitHub Actions path filter 监控，改动即触发校验与重建
- 数据分三层：`data/corpus/`（入仓语料索引）、`data/reports/`（构建产物）、`data/runtime/`（运行时队列）
- 所有产物带 `artifact_component / build_version / source_commit / generated_at` 元信息，可追溯到 commit
- 详情页 bundle 用内容哈希 `?v=xxx` 失效，并与数据里的 `templateSignature` 做版本一致性校验

### B. 核心数据模型（直接决定我们的改造量）

**语料层 —— 人物 Markdown 规范**（`storymap/docs/person_markdown_spec.md`）：
```
# 人物名
## 一、人物档案 → 基本信息（姓名/时代/出生/去世/享年/身份/历史地位/主要成就）+ 生平概述
## 二、人生足迹地图说明（行程概览/时间跨度/地理范围/重要节点数量）
## 三、人生历程与重要地点（按时间顺序）
   ### 🟢 出生地 / 📍 重要地点 / 🔴 去世地
   - 公元纪年 / 停留时间 / 位置（古称（今某省某市））/ 事迹 / 意义 / 名篇名句
## 四、生平时间线  表格：| 年份 | 古称 | 现称 | 事件 |
## 五、历史影响（对当时/对后世/历史评价）
## 人教版教材知识点 + 初高中阶段考点   ← 教学向专有，我们需替换
```
> 设计要点：语料是**人工可读可校订的 Markdown**而非裸 JSON——这是质量可控的关键，我们的巴黎语料库应沿用此思路。

**页面层 —— `__EXPORT_DATA__` 结构**（从 苏轼.html 实测）：
```
person{name, foreignName, description, descriptionHighlights[{phrase,category}],
       quote, shortReview, dynasty, aliases, birthplace, avatar, avatarSource,
       birth{date,location,lat,lng,coordSystem}, death{...}, lifespan,
       highlights{identities, achievements, works[], reviews[]}}
locations[]{name, ancientName, modernName, lat, lng, coordSystem,
            type(normal|birth|death), event, time, duration, significance,
            works[], quoteLines[]}                      ← 时空叙事的核心单元
coordinateSystem: "WGS84"
mapStyle{pathColor, markers{normal,birth,death}}
textbookPoints / examPoints                             ← 教学向，可替换
workTexts{作品名: 全文} / workSummaries{作品名: {title,aliases,authors,
          related_people,source_pages,era,genre,one_liner,summary,
          quote,quotes[],quote_policy}}                 ← quote_policy 是版权控制字段，值得保留
relatedGraph{center, nodes[], links[{source,target,label,confidence}]}
personRedirects{别名: 正名}  allPeopleNames[]  templateSignature  artifactMeta
```

**首页层 —— `stellar_home_data.json`**：
```
min_year/max_year/default_start/default_end               ← 时间轴域（-800~2000）
role_band_order[8] + role_band_labels{}                   ← 身份分档（军事/政治/文学/学术/思想/科学/艺术/其他）
search_capabilities{aliases, foreign_name, pinyin}
nodes[538]{person, birth_year, death_year, time_year, dynasty, quote, aliases,
           foreign_name, main_role_band, birthplace(_raw/_modern),
           birth_lat_wgs84, birth_lng_wgs84, file, has_story, seed,
           search_keys[], search_tokens[], search_pinyin[], works[], is_foreign}
edges[47]{a, b, type, label, confidence}
```
- 二段式加载：主数据 657KB 先渲染 → `_detail.json`(1.0MB) 后台补载 `review / work_summaries / relations / risk_level / audit_pass / audit_uncertain`
- **`risk_level / audit_pass / audit_uncertain` 把 AI 内容的可信度治理写进了数据模型**——这个设计我们必须继承并强化

**关系层**（`relations_export.json` / `people_knowledge_graph.json`）：
```
{source, target, relationship, weight, evidence, origin(bio|manual),
 source_dynasty, target_dynasty}
关系类型实际分布：并称31 / 相关人物4 / 会面3 / 同时代学人1 / 问学1
```
> **每条关系都带 `evidence` 证据字段**——这正是"语料库不能偷懒"该有的样子，POI 之间的关联也应沿用。

### C. 交互链路（Demo 穷尽式体验结论）

**站点信息架构**：纯静态站，一人一 HTML，无路由框架。
```
index.html 首页/全局星图
  ├─ [Tab] 时间分布 → Canvas 2D 星图（538 人按 time_year 散布，9 档朝代配色 + 呼吸动画）
  ├─ [Tab] 空间分布 → AMap 地图（502 marker + 胡焕庸线 + 省份 Top5）
  └─ 共享时间轴（-800~2000，非线性三段压缩，13 个朝代预设）
{人物}.html × 538
  ├─ #loc=N URL hash 深链（浏览器前进后退可用、可分享）
  ├─ 足迹时间轴（左） ⟷ MapLibre 轨迹地图（右）← 双向联动
  ├─ AI 人格化对话（支持 @其他人物 同框）
  └─ 知识点 + 关系图谱（跳转其他人物页，形成无限穿越）
```

**核心交互机制（值得完整继承的）：**

| 机制 | 具体实现 | 对我们的价值 |
|------|---------|-------------|
| **三级信息密度** | hover→tooltip 卡片；click→选中+联动；dblclick→跳页 | 避免信息过载，直接复用 |
| **时间轴三方联动** | 拖动时间窗 → 星图重绘 + 地图 marker 显隐/闪烁 + 计数实时更新 | POI 版可做"看 1920s 的巴黎" |
| **自动播放** | 每 ~2s 推进一站，时间轴卡高亮 + 地图 flyTo + 浮卡换内容 + hash 同步 | 故事线播放的现成实现 |
| **双向联动** | 点时间轴卡 → 地图飞行；点地图 marker → 时间轴高亮 | 故事线 ↔ 地图的核心交互 |
| **深链 `#loc=N`** | 分享出去直接落到第 N 站，全状态就位 | 单个 POI/单站可分享 |
| **轨迹曲线** | 按时间顺序连接各站，分段配色随生命进度渐变，带方向箭头 | 步行路线的可视化现成方案 |
| **关系图谱穿越** | 人物A → 关系卡 → 人物B → 无边界游走 | POI↔POI、POI↔人物 的关联穿越 |
| **多维搜索** | search_keys/tokens/pinyin 三套索引，12 档打分，**把匹配原因暴露给用户** | 中文搜法文 POI 必需 |
| **别名重定向** | personRedirects 苏东坡→苏轼 | 巴黎 POI 中/法/英多名必需 |
| **底图切换** | 矢量/影像/地形/3D 地形四档 + 全屏 + 生成图片 | 部分依赖境内服务，需评估 |
| **存疑标注** | UI 显式标「存疑」「史料未载」，数据层有 audit_uncertain | 娱乐向可转为"坊间传说"，变成特色 |

**视觉双主题叙事**：首页深空星图（深蓝 `rgba(8,15,36)` + 9 档朝代色 + 呼吸动画，氛围"浩瀚冷峻"）vs 详情页宣纸典籍（米白 `#F5F0E6` + 古铜金 `#8B6914` + 宋体衬线，氛围"温润书卷气"）。**这套"宏观→微观切换主题"的手法可以继承，但具体色板必须整体重做**——宣纸美学服务于中国古典语境，巴黎需要另一套视觉语言。

### D. 技术栈实况（决定境外可行性）

| 层 | StoryMap 实现 | 境内依赖 | 境外可行性初判 |
|----|--------------|---------|--------------|
| 首页地图 | **高德 AMap JS API 2.0**（`whitesmoke` 样式，502 独立 marker 不聚合） | 🔴 强 | 需替换 |
| 详情页地图 | **MapLibre GL JS** + GeoVis 星图地球数据源 | 🟡 MapLibre 开源可用，GeoVis 需替换 | 部分可用 |
| 3D 地形 | **Cesium** | 🟢 弱 | 可用，但成本待评估 |
| 降级 provider | AMap | 🔴 强 | 需替换 |
| 坐标系 | 源数据 WGS84，渲染前 `wgs84ToGcj02()` 纠偏 | 🔴 GCJ02 是境内特有 | **境外应直接用 WGS84，反而更简单** |
| 地理编码 | 链式 fallback：`AMap → Monid → Wikidata(P625) → Nominatim` | 🟡 已内置境外通路 | **重大利好，见下** |
| 前端 | 首页零框架 Canvas 2D + Tailwind CDN；详情页 Preact + 本地 vendor | 🟢 无 | 完全可用 |
| 语料/构建 | Python 3.11，Markdown → 解析 → 构建 → 静态产物 | 🟢 无 | 完全可用 |
| LLM | MiniMax M3 | 🟡 | 可换 |
| 埋点 | GA4 + 火山引擎 APMPlus | 🟡 | 按需 |
| 部署 | GitHub Pages / OpenDeploy / 火山云 ECS | 🟢 | 可用 |

**🎯 关键利好发现**：`storymap/script/map/geocode_providers.py :: resolve_city_geocode` 已实现**地域感知的 provider 路由**——`looks_foreign` 为真时**自动绕开高德**，走 `Monid → Wikidata(P625) → Nominatim`。也就是说境外地理编码的通路**代码里已经存在**，符合"最小化修改"原则，主要工作是把默认路由反转（境外优先）而非新建。

**🚩 关键风险发现**：`docs/geocode_todo.md` 记录了参考项目自己踩过的境外坑，且**尚未解决**：
- 中文境外地名歧义严重（"法国巴黎"可能命中国内同名地点，"意大利罗马斗兽场"同理）
- geocode 成功后无结果质量重排，命中错误时无自动纠偏
- 无"疑似命错但返回成功"的标注机制
- 其待办 P1 正是「把中文境外地名转成英文查询」（`法国巴黎 → Paris, France`）

> 对我们的启示：既然 MVP 只做巴黎、且 POI 是**预先策划入库**而非用户实时输入，可以**绕开这个难题**——直接在语料里写死经过验证的 WGS84 坐标（来自 Wikidata P625 / OSM），不依赖运行时地理编码。这是一个天然的降级方案。

**离线兜底数据现状**：`historical_places_index.jsonl` 67 条、`place_aliases.json` 136 条，**几乎全是中国古地名**（巴黎仅 1 条）。境外地名库需要从零建设——这与"语料库必须自建"的要求一致。

### E. 内容质量治理机制（必须继承并强化）

参考项目在 AI 生成内容的可信度上有一整套设计，这对我们"交叉验证、尽量无人工核实"的要求极具参考价值：

| 机制 | 实现位置 | 作用 |
|------|---------|------|
| 生成 Prompt 版式约束 | `story_system_prompt.md` | 强制结构化输出，明确"无法确定的标注存疑，不要编造" |
| 事实核查 Prompt | `fact_check_prompt.md` | 独立的核查环节 |
| CriticAgent 审校 | `runtime/legacy_agent/graph.py` | 查时间线顺序、地名精度、生卒年自洽、引文归属、身份混写；内置高频风险规则 |
| 修订循环 | Supervisor 条件路由 | validation 不过则回退重写，有最大轮次上限 |
| 低置信入队 | `hard_place_review_queue.json` | 解析不了的地名进人工审核队列 |
| 结构校验 | `validate_story_markdown.py` + CI | 必需章节、关键字段、时间线表头；只校验本次改动文件 |
| 数据层置信标记 | `risk_level / audit_pass / audit_uncertain / confidence` | 可信度进入数据模型 |
| UI 层诚实展示 | 「存疑」「史料未载」「定位可信度：高/中高/待复核」 | 不确定性对用户可见 |
| 版权控制 | `quote_policy: summary_only` | 有版权风险的作品只展示摘要不展示原文 |
| 关系证据 | 每条关系带 `evidence` 字段 | 关联不能凭空建立 |

> **`quote_policy` 尤其重要**：我们要处理大量现代文学与影视内容，版权敏感度远高于中国古诗词（已过公版期）。这个字段必须保留并强化。

| 18 | `tools/build/agents/geolocator.py` 内含独立高德调用，**不做 GCJ-02→WGS84 转换也不做边界校验** | 写回 HTML 的坐标与全系统 WGS84 基线有 **300~600m 系统性偏移**。境外场景我们纯用 WGS84，须确保删除此路径 |

**🟡 架构隐患**

- 启动命令三处不一致（Dockerfile / service.json / 文档各写各的），靠 `sys.path` 兜底绕过
- 配额与幂等仅落本地文件，而 `plan.json` 的 `persistent_paths: []` 导致每次部署清零；`x-forwarded-for` 不校验可信代理，配额可伪造绕过
- **双层重试放大**：`max_retries=2` × `retry_count+1`，最坏 9 次 × 60s = 9 分钟，远超任务 240s 超时
- `person_validator` 三条降级路径全部 `return "valid"`，LLM 抖动时**虚构对象的防线完全失效**（我们做内容校验时不能这么兜底）
- `tools/build/homepage/` 有三套重复实现并存（约 900 行死代码）且已开始漂移
- **三套「必需章节」校验规则互不相同**，同一份 md 在不同校验器下结论可能相反
- `langgraph>=0.2` 是死依赖（实际硬编码 Manual Runner）

**⚪ 产物冗余**

- 零引用产物：`star-office.html`(202KB)、`index.css`(49KB)、`homepage_custom.css`(48KB)、`world.json`(1MB)、`sw.js`
- `vendor/babel.min.js`(2.87MB) 已被构建期预编译取代，却仍被 534 份 HTML 引用
- 多处硬编码作者 macOS 绝对路径（`reviewer.py:38` 等），换机即失效
- README 引用的 `install.md` 等文件不存在
- **地图产物全站无版权与审图号标注**（`attributionControl:false`）——境外用 OSM/Mapbox 时 attribution 是**许可强制要求**，这条必须修
- 字形依赖 `demotiles.maplibre.org` 官方 demo 服务，**无 SLA**，生产不可用

> **结论**：「最小化修改」应理解为**保持架构与数据流不变**，而非逐行照抄。上述 #1/#3/#8/#18 以及 attribution、字形服务这几项，在复用时必须主动修正，否则会把已知缺陷带进新项目。

### H2. 置信度分级（字段级，不是 POI 级）

**先定义"独立源"** —— 这是多源验证最容易翻车的地方，必须硬编码判定表：

| 组合 | 独立？ | 理由 |
|------|-------|------|
| Wikidata ↔ 同语种 Wikipedia | **否** | Wikidata 大量条目由 Wikipedia 导入 |
| Wikidata ↔ 异语种 Wikipedia（有独立参考文献） | 弱（计 0.5） | |
| OSM ↔ Wikidata（当 OSM 带 `wikidata=*`） | **否** | 标签常由 Wikidata 同步 |
| opendata.paris.fr ↔ 任意 | **是** | 市政一手行政数据 |
| Mérimée ↔ 任意 | **是** | 文化部一手普查 |
| Open Plaques ↔ `plaques_commemoratives` | 部分（50m 内同人物计 1.5） | 可能是同一块实体铜牌 |
| Gallica 一手史料 ↔ 任意 | 强（计 1.5） | |

| 等级 | 阈值 | 呈现 | 文案约束 |
|------|------|------|---------|
| **L1 高置信** | ≥3 独立源一致（或 1 强源 + 1 独立源） | 无标记 | 可用肯定句 |
| **L2 中置信** | 2 独立源一致 | 正常展示 | 必须限定语："一般认为" |
| **L3 单源** | 1 源但为官方/一手 | + 灰色小标 | "据（来源）记载" |
| **L4 传说** | 单二手源，或多源矛盾无法裁决 | **强制"坊间传说"徽章** | |
| **L5 已证伪** | 存在权威否证 | **不作事实展示**，转为"辟谣卡片" | |

> **核心层准入**：主叙事所有事实 ≥L2 且至少一条 L1；L4 可出现但不能是承重点。

### H3. 冲突处理规则（命中即停）

| # | 规则 | 处置 |
|---|------|------|
| C1 | **源权威分层**：一手行政/普查 > Wikidata（带引用）> Wikipedia（多语种多数）> 媒体 > 旅游博客 | 取高层，低层不计源数 |
| C2 | **时间新鲜度**：涉及"当前状态"（营业/更名/易主）时，**最新有效源直接覆盖**，不做多数表决 | 例：passerelle Bichat → **passerelle Michèle Morgan**（2025.2 揭幕），旧源全部作废 |
| C3 | **数值容差**：年份差 ≤1 取早值；>1 降 L2 输出区间；坐标差 ≤50m 取一手源，>50m **进人工**（极少数人工路径之一） | |
| C4 | **同名歧义强制阻断**：名称相似度 >0.85 但距离 >500m 时告警 | 例：《筋疲力尽》Hôtel de Suède 在 15 quai Saint-Michel（**1993 已拆**），而 31 rue Vaneau 是完全无关的在营同名酒店。此规则专治这类错误——既会把用户送错区，又会给在营商户安上假电影身份 |
| C5 | **官方沉默即负面信号**：某类事实有权威系统性标注而该条恰好缺失时，置信上限锁 L2 | 例：巴黎市给《北方旅馆》标了桥，**唯独没给《天使爱美丽》标** |
| C6 | **实物 vs 记载矛盾**：铜牌与文献矛盾时**两者都存**，标"实物记载有误"，不裁决 | 例：Père-Lachaise 斯泰因墓碑卒年刻错、出生地拼成 "Allfghany"——**这类矛盾本身是内容金矿** |
| C7 | **台词 vs 实拍分离**：建两条独立记录，各标 `is_diegetic` | 例：《天使爱美丽》旁白说东站，画面是北站改的字 |
| C8 | 全不命中 | 降 L4 + 人工队列（预计 <2%） |

### H4. 「传说 vs 史实」徽章体系（娱乐向的差异化武器）

| 徽章 | 等级 | 文案模板 | 实例 |
|------|------|---------|------|
| 🏛 **有据可查** | L1 | （不显示） | 74 rue du Cardinal Lemoine 海明威 1922–23 居住 |
| 📎 **大家都这么说** | L2 | "多数资料指向这里，但没有一锤定音的证据。" | 运河上打水漂的那座桥 |
| 🗝 **只有一个出处** | L3 | "这件事只在（来源）里出现过一次。" | |
| ✨ **未经证实，但很好听** | L4 | "查无实据，不过我们决定留着。" | Le Consulat "毕加索梵高都来喝过" |
| 🔍 **著名的假故事** | L5 | "这个传说太有名了，有名到值得专门讲讲它是怎么假的。" | 今天的莎士比亚书店 ≠ 海明威去的那家；爱墙其实和《天使爱美丽》无关；Abbesses 站台实拍于 Porte des Lilas 幽灵站 |

> **L5 是产品差异化关键**：它把"我们做了交叉验证"从不可见的后台质量，变成用户能看见能转发的前台内容。**竞品讲传说，我们讲这个传说是怎么假的。**

**三条正交的实用标注**（与置信度无关，但直接影响差评率）：
🚪 只能在外面看 ｜ 🤫 私宅请轻声（如 place de l'Estrapade 有居民抗议与 "Emily Not Welcome" 涂鸦）｜ ⏳ 需预约/看季节

### H5. LLM 红线（工程强制，不靠 prompt 约束）

| 内容 | 允许 LLM？ |
|------|-----------|
| 坐标 / 门牌号 / 行政区 | ❌ 绝对禁止 |
| 年份 / 日期 / 时间区间 | ❌ 绝对禁止（只能复述已验证值，不得推断补全） |
| 人物-地点关联 | ❌ 绝对禁止（须来自 P551/P937/P20 或铭文） |
| 取景地事实 | ❌ 绝对禁止（须来自 `lieux-de-tournage-a-paris` 或 P915） |
| 营业时间 / 票价 | ❌ 绝对禁止（须带 `last_verified_at`） |
| 引文 / 台词 / 铭文原文 | ❌ 绝对禁止 —— **幻觉最高发区** |
| 中文译名 | ⚠️ 走固定译名词表，表外进人工 |
| 一句话钩子 / 氛围描述 / 过渡句 | ✅ 允许（仅可重组已验证事实） |

**工程手段**：LLM 输入是 **fact sheet（已验证事实的结构化 JSON）**而非自由文本；输出后跑**回指校验**——抽出文案里所有数字/专名/地址逐一比对 fact sheet，**出现表外实体即整条重生成**，连续两次失败降级模板文案。**把幻觉从概率问题变成可拦截的确定性问题。**

### H6. 端到端流水线（11 步）

```
[0] 候选池构建    → 约 3.5 万条（4 个市政集 + Overpass + Wikidata SPARQL + Mérimée + Open Plaques）
[1] 地址归一化    → canonical_address + BAN 编码｜门槛：可解析率 ≥95%
[2] 实体对齐      → 坐标 50m + 名称相似度 0.85 合并；OSM wikidata=* 直挂 QID
                    ⚠️ C4 同名歧义检测在此执行
[3] 交叉验证打分  → 字段级 L1–L5 + source_refs[] + conflict_log
                    门槛：坐标必须 ≥L2，否则 POI 直接淘汰
[4] 七维打分分层  → Hero / Story / Pin；排除规则前置
[5] 标签实体挂接  → 主题（规则+LLM 双路一致才落）/ 时代 / 街区
[6] Fact Sheet    → 序列化 ≥L3 事实｜Hero 层须 ≥5 条事实且 ≥1 条 L1
[7] LLM 文案生成  → 输入只有 fact sheet；L2/L3/L4 自动注入限定语模板
[8] 自动质检      → ①回指校验 ②限定语校验 ③敏感词 ④相似度<0.7 ⑤译名词表
                    连续 2 次失败 → Hero 进人工，Story/Pin 降级模板
[9] 入库发布      → Hero 需人工终审（唯一常规人工环节），Story/Pin 自动发布
[10] 持续校验(月) → 重跑 opening_hours / Wikidata / C2；状态字段 >90 天未验证则前台隐藏
```

> **人工介入仅 4 处**：① 14 个街区多边形一次性绘制；② 坐标冲突 >50m 仲裁（<1%）；③ 质检两连败的 Hero 条目；④ Hero 终审与精品线策展。
> **Story + Pin 层约 1,900 个 POI 全自动，无人工核实环节** —— 符合用户要求。

### H7. MVP 规模与工期建议

| 项 | 数量 |
|----|------|
| Hero（深度内容 + 人工终审） | **100** |
| Story（全自动） | **400** |
| Pin（仅列点） | **1,500** |
| POI 合计 | **2,000**（从 3.5 万候选筛出） |
| 人工精品故事线 | **12 条** |

- **阶段 0（3 天）先做许可决策再写代码** —— 骨干源是 ODbL，**share-alike 作用于"派生数据库"**，决定成品能否闭源商用。不先确认会导致 P1 全部返工。

### H8. 三个 MVP 必须做对的事

1. **状态类信息必须带 `last_verified_at` 与过期降级** —— 实测 Le Grand Véfour 已于 2025 年底易主、2026 年 5 月全新形态重开；passerelle Bichat 已改名。**巴黎文化 POI 的状态变化速度快过大多数团队预期。**
2. **线路时长必须诚实标注** —— 《爱在日落黄昏时》实测 10.1km / 3–3.5 小时，而电影只有 80 分钟。宣传成"实时走完电影"会直接产生差评。**诚实的数字是产品资产。**
3. **L5 徽章要在 MVP 就上线，不要等 V2** —— 它是把后台验证能力转化为前台传播点的唯一路径。

## 境外技术选型与竞品（调研结论）

### T1. 🚫 三个必须现在就规避的坑

1. **Google 全家桶在本项目上是死路**
   - **Photorealistic 3D Tiles 在 EEA 不可用**。官方原文："Photorealistic 3D tiles are not available"，EEA 账单项目请求会抛 **403**。自 2025-07-08 起适用，**法国在 EEA 内**。绕开需非 EEA 结算实体——这是法律问题不是技术问题。
   - **Geocoding 结果禁止长期存储**（只有 `place_id` 可留），与建知识库根本冲突。
   - **$200 统一免费额度已于 2025-03-01 取消**。
2. **许可分层必须在设计阶段就隔离**（不做来源标记会在商业化那天引爆）：
   | 许可 | 数据 | 影响 |
   |------|------|------|
   | **ODbL（share-alike 传染）** | Paris Volumes bâtis、`lieux-de-tournage`、OSM、ALPAGE | 会传染到衍生数据库 |
   | **Etalab 2.0（宽松，仅署名）** | IGN BD TOPO / LiDAR HD / RGE ALTI、BAN | 首选 |
   | **CC0（可商用可售卖）** | Paris Musées 15 万+ 图片 | 零许可成本 |
   | **CC BY-NC-ND（完全不能商用改编）** | DicoTopo | ⚠️ 本次调研中最严 |
   | 图像非商用 / 元数据开放 | Gallica | 商用需申请 |
3. **不要用 OSM 官方瓦片做生产**——OSMF 政策明文禁止预取，随时可断。

### T2. 推荐技术组合（MVP 月成本约 $20 + 一台小服务器）

| 层 | 选择 | 理由 | 月成本 |
|----|------|------|-------|
| 渲染库 | **MapLibre GL JS** | BSD-3，无 map load 计费，**唯一能同时服务中法两地** | $0 |
| 主底图 | **Protomaps pmtiles 自托管**（巴黎市域，maxzoom 14）+ Cloudflare R2 | 单个静态文件，无服务器无 key，R2 出站免费，**天然支持离线** | ~$0.05 |
| 风格底图 | **Stadia Maps Starter**（`stamen_toner_lite` / `stamen_watercolor`） | 文艺复古诉求的正统答案；Toner 三层可分离，历史图层可夹在中间 | $20 |
| 地理编码 | **BAN / Géoplateforme** | 2500 万法国地址、门牌级、周更、**50 req/s、Etalab 2.0 可永久存储** | $0 |
| POI 名检索兜底 | 自托管 **Photon**（Apache 2.0） | BAN 不做 POI 名与模糊匹配 | 服务器 |

**为什么不选 Mapbox**（尽管它 3D 巴黎表现最好、地标手工建模、地形零边际成本）：
1. **中国大陆完全不可用**（mapbox.cn 已停运）——若产品有中文/中国用户诉求，这是硬伤
2. 禁止缓存瓦片、无法离线——而文化漫步用户常在地铁或漫游状态
3. Permanent Geocoding $5/千且无免费额度，是 BAN（免费且允许永久存储）的纯增量成本

> 后续若要做高保真 3D 巴黎漫游，可把 Mapbox Standard 作为**独立付费增强模式**接入（3D 建筑+地标+地形全含在 map load 内，边际成本为零，5 万免费额度足够验证）。

### T4. 竞品结论：巴黎是个开口

**市场空白**：
- **Paris ZigZag** —— 本地头部品牌，58 万粉丝、月访问 50 万，**却没有地图、没有 App，而且刚退出体验业务**
- **Secret City Trails** —— 覆盖 50+ 欧洲城市，**唯独没有巴黎**
- **Questo** —— 巴黎有产品但薄且通用

**数据侧异常慷慨**：CC0 的 Atget/Marville/Carjat 全套巴黎旧影、ODbL 的带片名取景地数据、ODbL 的中世纪巴黎 GIS（ALPAGE，Vasserot 地籍图 910 幅已配准矢量化）、1,816 处历史建筑。

> **结论：内容原料是免费且顶级的，缺的是把它组织成"可走的故事"的产品。**

**侧翼威胁**：Smartify 拿了 £1.5M、1,200 家机构、200 万用户，新投资人公开目标是成为"旅行者搜索、选择、消费文化内容的首选 App"——一个博物馆应用向城市尺度外扩，是这个空间最可信的入侵者。

## 巴黎内容素材实测结论（影视取景地专项）

> 这一节是**方法论验证**：用「巴黎市政取景许可数据 + 多源交叉」去核实网上流传的取景地说法，结果发现**错误率极高**。这直接证明了 H2–H5 那套验证机制的必要性，也产出了一批 L5 级的优质内容。

### P1. 骨干数据源实测

**`lieux-de-tournage-a-paris`（巴黎市政取景许可）**
- 覆盖 **2016–2024**（早于此的影片查不到，需其它源补）
- ⚠️ 字段陷阱：**`coord_x` = 经度，`coord_y` = 纬度**（与直觉相反）
- ⚠️ **影片以代号报备**：《碟中谍6》报备名是 **"GEMINI"**，用 `MISSION` 查返回 0 条相关结果 → **知识库必须建「片名别名表」**
- 地理编码用 `api-adresse.data.gouv.fr`（BAN）实测可用；Nominatim 在部分环境被墙

**《爱在日落黄昏时》**（80 分钟近实时，**15 天拍完**，最长斯坦尼康镜头约 11 分钟）：

### P4. 对数据模型的三条硬性要求（从实测反推）

1. **必须有片名别名表** —— 代号报备（GEMINI）、中英法多名、系列作编号
2. **必须区分 `is_diegetic`（片中设定地）与实拍地** —— 且两者都要能上地图，因为用户两种都会找
3. **必须支持「主体，非取景地」类型** —— 红磨坊这类"名气来源于此但没在此拍"的 POI，不标清楚就是错误信息

| **IMDb / TMDB** | ❌ 双双出局：均**无取景地字段**，且 IMDb 仅限非商用、TMDB 点名 LLM 用途为商用 |
| **Open Plaques** | 数据 PDDL 公共领域 ✅，但**照片是第三方 CC BY-NC-ND** ❌ |
| **ODbL 传染性对策** | OSM/APUR 数据**单独建表、查询时 join、不提供批量导出** → 停留在 Produced Work 一侧 |
| Overpass | ❌ 官方明令**禁止把公共实例作为 app 后端**，必须一次性抽取自建 |

> ⚠️ 另需注意：任务书中列举的 `liste-des-cafes-a-un-euro`、`sites-touristiques`、`monuments-historiques`、`musees`、`sepultures` 等数据集 ID **在巴黎门户全部返回 404**，实际不存在。

### D6. ⭐ 差异化内容层：「铭牌怎么说 vs 实际发生了什么」

调研共推翻 **40 条广泛流传的错误说法**，其中最有价值的是——**巴黎官方铭牌本身就有错**：

| 铭牌说法 | 实际 |
|---------|------|
| 皮雅芙生于贝尔维尔街 72 号台阶上（1963 年铭牌） | **出生证明写的是 Tenon 医院** |
| 普罗可布咖啡馆自家铭牌写 1656 年 | 实为 **1686 年**，早写了三十年；且原店 1872 年就关了，现在是 1957 年重开的餐厅 |
| 雨果故居博物馆说 1832 入住 | **同一面墙上的铭牌说 1833** —— 两个官方来源差一年 |

其它高价值辟谣：《天使爱美丽》照相亭在**北站**不是东站（"NORD"被数字改成"EST"）；圣叙尔皮斯日晷**不是**巴黎子午线（真子午线在东侧约 100 米，由 Arago 铜牌标记，1994 年埋 135 枚现存约 100 枚）；《火车进站》**不在**卢米埃首映片单里（影史最顽固的神话）；拉雪兹**不是** 30 万人下葬而是**逾 100 万**；福煦大街 84 号是**保安处 SD** 不是盖世太保。

> **这是目前没有任何竞品地图拥有的角度**，且与 H4 的 L5「著名的假故事」徽章完美咬合。

### D7. 时间分层建议（7 段，与铭牌 `periode_1` 字段天然对齐）

1. **旧制度/启蒙**（–1789）· 铭牌 74 条
2. **大革命与帝国**（1789–1815）· 铭牌 54 条
3. **十九世纪浪漫主义与奥斯曼**（1815–1870）
4. **公社与美好年代**（1871–1914）
5. **迷惘的一代**（1918–1939）← 内容最厚、国际认知度最高
6. **战后与存在主义**（1940–1959）← 铭牌 1,105 条，数据最厚
7. **新浪潮到当代**（1960–今）

> 妙处：**每段都同时有「人物+作品+影视+事件」四类内容**，不会出现某段只有干巴巴的历史。建议 5、6 段作为首发主推。

### D8. 首发选点建议（28 个，优先选「一点挂多线」的 POI）

**核心原则：优先选能同时挂 3-5 条故事线的 POI**，让首发内容密度看起来远超实际条目数。典型如：
- **旺多姆广场** = 肖邦逝世 + 《Lupin》黑珍珠劫案 + 库尔贝推倒纪功柱（**一点三线**）
- **圣艾蒂安杜蒙教堂台阶** = 《午夜巴黎》+ 《Lupin》S2（许可数据佐证）
- **红衣主教勒穆万街 74 号（海明威）与 71 号（乔伊斯）** = 隔三个门牌、两块铭牌隔街相望的天然叙事

**墓地作「聚合型 POI」处理**：不铺单个墓点，做成"园内名人地图"下钻页 —— Wikidata P119 现成提供 7,345 + 1,886 + 1,115 人，零成本深度内容。

### D9. ⭐ 内容判真法则（可直接写成入库判据）

故事线调研中提炼出的一条实用规则，用于判断「某某名人常来这家店」的真伪：

> **如果一条掌故能说清「为什么是这家、在哪一年、有什么具体细节」，它大概率是真的；如果只是一串名字，那是菜单的一部分。**

**正例（可判 L1）：**
- 花神咖啡馆 —— 萨特波伏娃常驻**有具体原因**：1939 年老板 Paul Boubal 装了烧煤炉子，而占领期巴黎公寓没有取暖燃料。有萨特本人引语 + 1947 年《巴黎晚报》讽刺作息表作同时代旁证，**四源一致**
- Le Tabou —— **1947 年 4 月 11 日开张**，Vian 三兄弟组乐队（Boris 小号 / Alain 鼓 / Lelio 吉他），巴黎市立图书馆一手记载
- 双叟的 Prix des Deux Magots（1933，首奖 Raymond Queneau）与 Lipp 的 Prix Cazes（1935）—— **有官方页面与完整历届名单**

**反例（应判 L4）：**
- 几乎每家左岸老店的官网都会列一串名人清单（海明威、毕加索、萨特、加缪、杜拉斯、鲍德温…）。这些人确实在这一带活动过，但**「某某是本店常客」和「某某来过一两次」之间的距离，在营销文案里被抹平了**

> **工程化落地**：入库时要求每条人物-POI 关联必须填 `why_here`（为什么是这家）+ `when`（哪一年）+ `detail`（具体细节）三个字段，三者缺一即自动降级为 L4「坊间传说」。这恰好呼应参考项目关系边的 `evidence` 字段设计。

### D10. 内容组织的两个额外洞察

**① 同一街区可以承载态度相反的两条线**
海明威线与《午夜巴黎》线在地理上高度重叠（同一家书店、同一批人名），但态度完全相反——**一条告诉你那是假的（莎士比亚书店不是海明威那家），一条告诉你假的也很好（Gil 向往的 1920s 本就是想象）**。两条并排放在产品里，本身就是一个编辑主张。

**② 一条线内可做「日/夜」双段结构**
《午夜巴黎》线天然可拆：白天走艺术（Rodin / Deyrolle / Orangerie）= Gil 清醒时的巴黎；夜里走浪漫（教堂台阶 / Polidor / 桥）= 他喝多之后的巴黎。**分界点就是钟敲十二下。**

**③ 地理巧合本身就是叙事**
波伏娃 1955 年搬进 11 bis rue Schoelcher，那条街紧贴蒙帕纳斯公墓的墙；她在那扇门后写了三十一年，1986 年被葬到对面。**从第 7 站走到第 8 站只需五分钟，而那五分钟走完的是三十年。** 萨特同理——最后住的 29 bd Edgar-Quinet 正对公墓，他形容那栋楼"毫无魅力"，然后就在它对面躺下了。

> 这类「相邻 POI 之间的距离本身有意义」的关系，值得在数据模型里单列一种关联类型。
